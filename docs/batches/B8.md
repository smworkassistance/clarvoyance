## Research findings the plan is built on (verified 2026-09-26)
1. **Upload stuck at 0 %**: v246 was verified against REAL Bunny with tus `chunkSize` = default (one request). v247 changed to `chunkSize: 1 MB` (`CFG.chunkSize`, index.html ~line 22595) and was only tested against a LOCAL tus server (qa/tests/video-upload.spec.js), never real Bunny. Bunny's docs (bunny.net/docs/stream/tus-resumable-uploads) list required headers but no chunk size; community reports of "stuck at 0 %" with Bunny recommend 5 MB chunks. → Prime suspect. Must be proven with a REAL upload (T-060).
2. **Auto-mute**: (a) Android app: Capacitor's Android WebView has `mediaPlaybackRequiresUserGesture = true` by default → every autoplay with sound is refused → our fallback mutes. `MainActivity.java` is an empty `BridgeActivity` today. (b) Chrome: sound autoplay allowed after the user has interacted with the page (sticky activation) and the YouTube iframe has `allow="autoplay"` (YT.Player sets it). (c) iPhone Safari: sound needs a user gesture per play; a cross-origin YouTube iframe can't get it from our page → YouTube starts muted; show a clear "Tap for sound 🔊" pill (our UI, outside the player) that unmutes on tap (the tap is a real gesture on our page → call `player.unMute()` synchronously inside the tap handler).
3. **Black borders**: our stage box doesn't match the video's real shape, so YouTube letterboxes. YouTube Data API `videos.list` with `part=player&maxHeight=…` returns `embedWidth/embedHeight` (the true aspect) — the Worker already calls `videos.list` (1 unit per 50 ids) so adding `player` to `part` costs **0 extra units**.
4. **Swipe on the video**: a cross-origin iframe swallows touch events, but a NATIVE scroll container (CSS scroll-snap) still scrolls when the finger starts on a non-scrollable iframe (scroll chaining) — this is how Shorts-style web feeds work, with no overlay. → Rebuild the players as scroll-snap lists (T-064). Must be verified on real touch emulation; fallback documented in the task.
5. **YouTube start time**: an embedded YouTube player needs ~1–3 s to start from cold (iframe + player JS + first segment); re-hosting YouTube files is forbidden by YouTube ToS. Best legitimate: poster (thumbnail) instantly + next player already created, buffered and paused (v250 does this in Vibe only; Discover `#exv` does NOT — it `loadVideoById` on each next). True zero only with our own files → Clar Reels (own MP4 on Bunny CDN, `preload` the next 2).
6. **Feed Bunny videos 5–6 s black**: inline player loads hls.js from jsDelivr on demand, then HLS manifest → variant → first segment; `preload="none"`. For 10–35 s clips progressive MP4 (`play_480p.mp4`, fallback ladder 720/480/360/240 already exists in `_rlAttach`) starts faster and can be prefetched.
7. **Pexels API**: free, 200 requests/hour, 20,000/month, video search `GET https://api.pexels.com/v1/videos/search?query=…&orientation=portrait`, `video_files[]` with `quality,width,height,link`. Attribution: prominent link to Pexels + "Video by <name> on Pexels" when possible. Hot-linking not addressed → re-host via Bunny Stream's **fetch-from-URL** API (`POST https://video.bunnycdn.com/library/{libraryId}/videos/fetch` body `{"url": "<pexels mp4>", "title": "…"}` with `AccessKey` header) so files live on our CDN.
