## What v270 actually is
Short "Listen" audio clips that explain how to use a section (teal bar), plus one affirmation audio per charger container (gold bar). Finalise-first: nothing reaches a user until the owner writes/drafts the text, generates the audio, listens, and taps Finalise. Editing the text un-finalises it again.

## How to add audio for a scope (owner's own workflow)
1. Open `admin.html` → **🔊 Audio** tab.
2. Pick a voice for each language under **Languages** (Load voices → choose → Save voice) — only needs doing once per language.
3. Open a scope. Write the text, or type a prompt and press **✨ Draft with AI** (fills the text box only, never auto-saves).
4. **💾 Save text.**
5. **🎙 Generate audio**, listen to the preview.
6. **✓ Finalise.** It now shows in the live app within the next page load (and ~10 min for GitHub Pages' own CDN to pick up anything code-side, but audio text/finalise changes go through Supabase directly, not the CDN, so they're closer to instant).

## Key technical facts for next session (read before touching scope audio again)
- **The Goal tab was redesigned in v264** — `#v264-root` is the real container (filled by the app's own JS, content replaced wholesale). The CSS rule `#goal-row.v264 > :not(#v264-root){display:none}` permanently hides the old `#goal-body-major` markup — don't mount anything there again.
- **Static vs. re-rendered mount points**: most scopes are static markup (mount once at boot is enough). Chargers, Tools' Mental Reset panel, and Goal's `#v264-root` are **rebuilt by the app's own JS**, so they use a `childList` `MutationObserver` scoped to just that one container (`watch('ch-main', ...)`, `watch('tl-main', ...)`, `watch('v264-root', ...)` in the v270 script block near the end of `index.html`) — a one-time mount there gets silently wiped the next time the app re-renders that area. If a future scope's mount point turns out to also be app-rebuilt, use the same `watch()` helper, don't assume a static mount is safe without checking.
- **Charger container keys are slugged**, not raw (`auSlug()` in both `admin.html` and the app script, must stay identical in both places) — a real category id can have odd characters (confirmed live: `"Monk "` with a trailing space, same quirk CLAUDE.md's v181 entry already documents for admin.html's charger-category field).
- **`qa/tests/admin-audio-v270.spec.js` must navigate to the literal `/admin.html`**, never `/` — `ops/verify.js` serves whatever `QA_TARGET` is at `/` for the WHOLE suite, so a spec that relies on `/` being admin.html only works when run standalone with `QA_TARGET=admin_v270.html`.

## Machine note (read before running the full verify again)
This machine has 3.8GB total RAM and is frequently down to <0.2GB free with VS Code + Claude Code + the browser all open. The full `ops/verify.js` run (125 tests, Chromium) crashed twice and hung once (a full hour, near-zero CPU, not visible as a crash) this session before a clean run finally completed. If it crashes/hangs again:
1. Check `Get-CimInstance Win32_OperatingSystem | Select FreePhysicalMemory` — if near 0, that's almost certainly why.
2. Use `Get-Process | Where ProcessName -match 'node'` and check CPU time growth over a minute or two — near-zero growth over several minutes means it's actually stuck, not just slow; kill it (`Stop-Process`) and retry, ideally after the owner closes some other heavy apps.
3. Don't trust a `| tail -N` pipe for live progress — it buffers until the whole process exits. Run `node ops/verify.js` directly (no pipe) if you need to see progress as it happens, or watch the output file with `Monitor`/`tail -f`.
4. For spot-checks that don't need the full suite, reusing an already-open Chrome tab via the chrome-devtools MCP tools is much lighter than spawning a new Playwright browser — this is how all 18 scope-audio mounts were hand-confirmed this session when Playwright itself couldn't run.
